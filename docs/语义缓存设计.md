# 问数语义缓存设计

语义缓存用于复用完整统计问题对应的成功 SQL，接在问题改写之后、关键词抽取之前。它与原有字段/指标知识检索使用同一套 Qdrant 和 Embedding 服务，独立保存缓存数据。

## 数据与职责

`SemanticCacheService` 接收已有 Qdrant 异步客户端和 Embedding 客户端。`DataAgentContext` 注入服务对象，`DataAgentState` 保存本轮匹配结果。外部连接不进入图的业务状态。

| 项目 | 当前实现 |
| --- | --- |
| 集合 | `chatbi_semantic_cache` |
| 向量维度 | 读取 `app_config.qdrant.embedding_size`，现有配置为 `1024` |
| 距离 | Cosine |
| 查询 | `search_cache(query_text, score_threshold=0.95)`，最多返回最高分的一条 |
| 写入 | `save_cache(query_text, sql, meta=None)`，由成功查询完成逻辑调用 |
| 点 ID | 由集合名和完整问题生成确定性 UUID，相同问题更新同一个点 |
| Payload | 完整问题、SQL、附加元数据、UTC 保存时间 |

首次访问时检查并创建集合，同时容忍其他请求已经创建集合的竞争情况。已有集合会核对维度和距离；不兼容时上抛异常，由查询路径降级，不删除原集合。Embedding 返回维度也会校验。

检索使用改写后的完整 `query`，不使用“那华东呢？”这样的省略原话。返回记录包含 ID、完整问题、SQL、元数据和相似度；没有记录、低于阈值或最高分记录缺少非空 SQL 时返回 `None`。

## 工作流路由

| 触发条件 | 路径 |
| --- | --- |
| 意图为 `clarify` / `out_of_scope` | 原有回复节点，结束本轮，不查缓存 |
| 意图为 `follow_up` / `new_topic` | 使用完整问题查询缓存 |
| 缓存命中 | 同时写入 `cached_sql` 与原有 `sql`，设置 `is_cache_hit=True`，直接进入 `validate_sql` |
| 缓存未命中或读取异常 | `extract_keywords` → 原有完整链路 |
| 缓存 SQL 校验失败 | 清除命中状态，设置回退标记，重新进入关键词抽取 |
| 普通 SQL 校验失败 | 保留原有校正一次后执行的路径 |

失效缓存回退完整链路，是因为原有 `correct_sql` 需要表、指标、日期及数据库上下文；这些信息在缓存命中路径中没有准备，不能直接进入校正。

缓存正常命中后仍重新执行 SQL，返回本次数据库结果。缓存不保存结果行，也不替代最前面的改写模型调用。

## 保存与异常处理

QueryService 正常消费完图输出，并且最终 `query_succeeded=True` 时，先记录成功历史。仅当最终 `is_cache_hit=False`，才异步写入完整问题与最终 SQL；当前元数据包含本轮意图。

保存采用 `await`，请求会等待异步写入完成后正常结束，没有新增后台队列。写入异常记录警告，不撤销已成功的查询和会话记录。

缓存校验失败后走完整链路，若最终成功，则允许重新保存本轮问题。相同完整问题会更新同一点；不同文字的问题可能产生新点，因此该逻辑不等同于主动删除全部失效缓存。

## 进度事件

缓存命中示例：

```text
event: progress
data: {"type":"progress","step":"cache_hit","status":"success","message":"命中高频问数语义缓存，直接复用已验证 SQL，继续校验与执行..."}

```

缓存 SQL 校验失败时输出 `cache_fallback` 进度。JSON 保留已有 `type` 字段，现有前端按 `data:` 解析的方式可以继续消费。前端固定流程图的专门缓存分支尚未新增。

## 验证

[测试文件](../tests/test_semantic_cache.py) 共 15 项离线测试，于 2026-10-16 执行通过：

- 缓存服务 6 项：集合创建、存取与同问题更新，最高分及可调阈值，精确阈值边界及空 SQL，向量维度与空输入，不兼容集合，首次创建竞争及真实失败传播。
- 工作流 9 项：命中跳过检索生成但保留校验执行，未命中完整链路与保存，新话题查缓存，澄清/超范围绕过，读写故障降级，失效缓存回退，原有校正路径，执行失败不保存，两轮请求先写后命中。

测试保留实际图的边和条件路由，以内存 Qdrant、人工向量及模拟模型/数据库替代外部访问；精确 `0.95` 边界通过模拟返回分数验证。两轮用例贯穿缓存服务与工作流，但不评估真实中文问题的相似度。

```powershell
uv run python -m unittest discover -s tests -v
```

新增代码的 Ruff 检查通过。真实服务联调、命中率、误命中率、耗时和成本对比尚未完成。

## 适用边界

- `0.95` 是默认匹配阈值，不是 95% 正确率。SQL 能校验执行不代表它与新问题的筛选条件、指标口径一致。
- 不缓存结果行，可以重新读取数据；但 SQL 如果写死了此前的时间范围，仍可能对“今天”“本月”等问题过期。
- 当前没有 TTL、容量淘汰、模型或元数据版本隔离，也没有按用户、租户和权限过滤。
- 相同文字使用确定性 ID，不同措辞仍可能重复保存；首次集合创建容错不等于完整的并发写入治理。
- 数据库校验通过后若执行失败，仍返回原有错误，没有增加执行阶段的自动重试。
- 断连和取消时的写入行为，以及真实故障和压力场景，未专项验证。
