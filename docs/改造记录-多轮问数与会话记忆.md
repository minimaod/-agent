# 个人 Agent 改造记录：多轮问数与会话记忆

记录日期：2026-10-15
当前阶段：基础组件与局部验证完成，完整流程接入待完成。

## 1. 改造背景与目标

基于 didilili/shopkeeper-agent 第17章工程继续学习和改造。

原有问数链路围绕本轮 query 处理，无法直接理解“那华东呢”
这类依赖历史的省略问题。

计划在原有关键词抽取之前增加问题理解与改写：
先判断是否需要历史，再把追问补成可以独立查询的完整问题，
交给原有检索、SQL生成、校验与执行链路。

第一阶段目标：
- 条件继承、替换和追加。
- 分组调整。
- 新话题识别。
- 按会话编号隔离历史。

第二阶段目标：
- 引用历史查询结果，例如“刚才排名第一的商品”。

上述目标尚未全部完成。

## 3. 实现过程与职责划分

### 第一步：定义什么信息值得留下

新增 SuccessfulTurn，保存一轮成功查询的：
- raw_query：用户原话。
- query：实际交给问数链路的问题。
- sql：执行的 SQL。

它保存的是成功查询记录，不是本轮所有中间数据。
目前还没有保存查询结果，不能据此回答历史结果引用问题。

### 第二步：按会话编号管理历史

新增 ConversationMemoryStore：

session_id → 多条 SuccessfulTurn

同一编号可以保存多轮记录；不同编号对应不同列表。
get_history 返回列表副本，避免调用方清空返回值时破坏内部历史。

当前使用进程内字典，程序重启后历史会丢失。

### 第三步：区分本轮状态与跨轮历史

DataAgentState 描述本轮执行需要的数据：
会话编号、原话、待查询问题、历史，以及检索和 SQL 中间状态。

State 的类型定义不会自己保存历史。
QueryService 负责读取会话历史、初始化本轮 State，
并在本轮正常结束且具有成功标记后追加成功记录。

### 第四步：识别查询是否成功

run_sql 在 SQL 执行成功后返回 query_succeeded=True。

QueryService 同时接收两类图输出：
- custom：节点主动发送的进度、结果等消息，继续包装为 SSE。
- values：图的状态快照，用于取得最终状态和成功标记。

历史写入代码以成功标记为条件。
这一集成行为目前经过源码核对，尚未通过完整接口验证。

这里的“成功”指 SQL 执行成功，不等于模型理解一定正确。

### 第五步：准备问题理解与改写

新增 QueryRewriteResult，约定四种意图：
- follow_up：依赖历史的追问。
- new_topic：独立问题或新话题。
- clarify：信息不足，需要澄清。
- out_of_scope：超出电商问数范围。

提示词规定：先判断是否追问，再决定是否继承历史；
替换条件时去掉旧值，追加条件时保留相关旧值。

format_history 将历史原话和完整问题整理为 JSON，
当前不把历史 SQL 放进改写提示词。

调用链为：

提示词 → 现有模型 → PydanticOutputParser

拼装调用链不会发起请求；
执行 understand_query 中的 ainvoke 才会调用模型。

解析器校验输出结构和意图枚举，
不能保证改写语义正确。目前也未强制校验不同意图下的字段组合。

## 7. 学习中需要记住的区别

- 会话编号关联一段对话，一段对话中仍可能切换话题。
- 本轮 State 保存执行过程，成功历史保存跨轮参考信息。
- 手写模型输出用于测试解析器，真实模型调用用于检查理解行为。
- 模型调用成功不等于后面的 SQL 查询已经成功。
- 多轮追问要参考历史中的完整问题，不能只叠加省略原话。
